# User Taste
- Builds Windows desktop game-automation tools in Rust (Cargo projects). Confidence: 0.7
- Treats the existing Elorin project as the canonical reference implementation and expects the agent to look up how something was already done there (e.g. "check [Elorin] how we did the mousemove to target, sleep a bit and click") and carry that proven pattern forward — rather than reimplementing from scratch. Confidence: 0.85
- Works incrementally, one small piece at a time: get a single feature "perfect" (e.g. slot highlighting exactly right) before moving on. Confidence: 0.6
- Persists calibrated outputs (e.g. computed slot coordinates) to be reused by later projects instead of recomputing them. Confidence: 0.6
- Prefers staged development: first ship a minimal stage that only gathers/stores data to a file, deferring downstream consumers (dashboards, automation) to later phases. Confidence: 0.6
- Provides PNG sprite assets (digit glyphs, button icons) for template matching rather than relying on generic OCR. Confidence: 0.5
- Demands correctness over speed: expects outputs to be exactly right ("we have to be perfect"), with zero tolerance for wrong values when an incorrect result could trigger a costly downstream action. Confidence: 0.7
- Wants debug/diagnostic visualization kept separate from the production UI and toggleable off, so a clean, dedicated overlay showing only useful information can ship later. Confidence: 0.6
- Open to installing third-party tools/dependencies as long as they are best-in-class for the task; prioritizes quality/accuracy over minimizing dependencies ("the better the better"). Confidence: 0.75
- Wants the actual computed output (e.g. the raw recognized text, a captured quantity) surfaced in the logger/console so he can personally confirm a feature is really working end-to-end rather than trusting it silently; expects this proactively whenever new fields are extracted. Confidence: 0.9
- Expects debug visual indicators (overlay boxes, regions) to accurately match the area/value actually being processed; a misaligned box signals to him that data may be clipped or captured incorrectly. Confidence: 0.75
- Prioritizes data integrity for downstream analytics: wants duplicate/stale readings filtered out so they don't skew aggregates (e.g. average prices) in the dashboard. Confidence: 0.6
- Prefers to persist a record only when a real change actually occurred (storing it with the change's timestamp) and to skip no-op/unchanged scans. Confidence: 0.6
- Wants ancillary data captured per scan and linked to the item — the item image and the seller name — to help disambiguate/identify duplicates rather than relying on the item name alone. Confidence: 0.5
- Wants captured image assets isolated from their source UI: prefers the panel/background keyed out to a transparent PNG (consumable as a clean asset) rather than a raw crop that still includes the game UI behind it. Confidence: 0.55
- Reports bugs tersely (e.g. "still making some mistakes, not perfect yet", or just pasting a raw error/parse log with no prose) while attaching raw artifacts — a screenshot of the current state plus a paste of the full console/log output — rather than writing explanatory prose, expecting the agent to self-diagnose from those runtime artifacts (last captured frame, output JSON, logs). Confidence: 0.75
- Prefers analysis/dashboard tooling to be online-hosted and device-agnostic (reachable from phone, laptop, or any standby device) rather than a local-only desktop app, so it stays continuously up to date. Confidence: 0.6
- When ranking "best" options (e.g. items to invest in), wants real-world costs applied — notably factors the 10% market fee into profitability rather than comparing raw prices. Confidence: 0.6
- Insists solutions be free of cost: no paid hosting, no purchased domains, no subscription services — wants whatever can be implemented for free (free tiers such as Supabase/GitHub Pages). Confidence: 0.85
- Wants dashboards to offer multiple time-window rollups (per day/week/month) plus finer trend views (hourly, daily) and searchable/filterable item lookup that highlights the matched item. Confidence: 0.5
- Expects the agent to carry out as much of the setup/deployment as possible autonomously through available integrations/MCP tooling (creating repos, publishing, wiring config), rather than handing him manual multi-step instructions ("can't you just do that yourself with mcp?"). Only wants a manual step when it is genuinely impossible for the agent. Confidence: 0.7
- Expects web dashboards/views to update themselves live on a short interval (seconds, not minutes) without any manual refresh/reload step. Confidence: 0.65
- Wants previously gathered per-item assets (e.g. captured item icons) surfaced in new outputs/UI so items are visually represented, rather than leaving collected assets unused. Confidence: 0.5
- Insists on retaining full manual control over anything that automatically spends or mutates on his behalf: each item needs its own explicit opt-in (e.g. a per-item checkbox) plus a user-set threshold, all gated behind a master switch — never an autonomous decision. Confidence: 0.85
- Wants safety guardrails/caps on automated spending: per-item quantity limits that auto-disable the item once reached, and a separate ration for rare jackpot/high-margin events (e.g. only a couple per session), with those counters scoped strictly to the items he explicitly opted in. Confidence: 0.7
- Wants lists/panels to be data-driven and self-updating: every unique entity discovered is listed automatically (with its icon, name, trends, etc.) as new ones appear, rather than requiring manual registration. Confidence: 0.6
- Privacy-conscious about anything that reveals his activities: wants sensitive pages/features gated behind sign-in (showing nothing until authenticated) and not linked from public pages, so a random visitor can't stumble onto what he's doing. Confidence: 0.6
- After changing something himself (e.g. a setting in a UI), expects the agent to independently verify the full data round-trip end-to-end — that the change persisted and is actually readable by the consuming component — and to report back what he changed by reading it from the live store rather than asking him. Confidence: 0.55
- Specs out automation/UI flows as ordered, step-by-step sequences with explicit numeric parameters — concrete timeouts (e.g. 5 s / 3 s / 1000 ms pauses) and quantities — rather than high-level prose. Confidence: 0.6
- Models any "wait for / look for an element" step as a search-until-found polling loop bounded by an explicit breakout timeout (give up after N seconds), not a fixed sleep. Confidence: 0.6
- Pins down desired logic with concrete worked examples/edge cases (e.g. "667 of a 1000 cap → buy 667; only 250 left → take 250") so behavior at boundaries is unambiguous. Confidence: 0.55
- Favors consolidating configuration/controls into the website UI over local config files (which need a restart to take effect), and questions features that lack a clear use case ("i don't see the use case of it") — prefers removing redundant/overlapping switches to having multiple controls that all must be right. Confidence: 0.6
- Wants solutions that generalize uniformly across all cases rather than being special-cased/tuned per instance: expects one method that works for every item regardless of individual variation (e.g. each icon having a different outline shape), and pushes back when an approach would need per-item hacks. Confidence: 0.75
- Demands explicit validations and failsafes at every step of an automated flow: each step's outcome must be actively verified (or the action safely aborted) rather than assumed, so a coincidental match or phantom result can never trigger a click or get recorded. Confidence: 0.8
- Expects a new feature/flow to succeed on its first real live attempt ("aim at first time right"), not merely to eventually work after iterations. Confidence: 0.6
- Pushes back when the agent repeatedly leans on a verification signal he considers irrelevant (e.g. re-citing coin/currency balance as proof a purchase worked); wants evidence drawn from the object actually being acted on (e.g. the item's own state) and expects the agent to drop lines of reasoning he's ruled out rather than raising them again. Confidence: 0.55
- Expects iterative changes to preserve already-working behavior and is quick to suspect the agent broke something ("u did something which perhaps f'd up the matching method"); runs the live test himself, often more than once, before reporting back. Confidence: 0.5
- Wants input automation to emit only deliberate inputs and never stray keystrokes (e.g. an Escape press) that could exit or disrupt the current in-game context; flags any observed side-effect input as a bug to fix. Confidence: 0.5
- For vision/detection, wants the threshold calibrated precisely from real captured frames ("a perfect threshold would be great") rather than tuned by eye; is comfortable proposing the distinguishing signal to key on himself (e.g. the item's glow) and accepts frequent polling (even sub-millisecond) to catch a signal that appears and disappears, expecting the agent to derive an exact, robust threshold and verify it against the captured artifacts. Confidence: 0.5
